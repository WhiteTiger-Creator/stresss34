A failed pager-policy rollout left the responder host degraded: the scheduled metrics-rollup compile no longer runs cleanly under its service account, and the rollup service it drives was left broken. The primary deliverable is to recover the host so the scheduled compile both runs and rotates correctly as its own service account — and, because a recovered schedule that runs a broken service still ships bad pages, to repair that service so the scheduled run produces trustworthy output.

**Host recovery (primary).** Bring the host to the state defined in `/app/docs/deployment_runbook.md`:

- the dedicated `svc-metrics` **system** account with no interactive login shell;
- the operator wrapper `/usr/local/bin/rollup-metrics` — root-owned, mode `0755`, forwarding its arguments to the compiler and running it **as the invoking user** (it must not `su`/`sudo`/`setpriv`/`setuid` or otherwise change identity — selecting `svc-metrics` is the cron drop-in's job), and lock-aware: when `/var/lock/metrics-rollup.lock` exists it exits `75` and writes nothing;
- the `/etc/cron.d/metrics-rollup` drop-in (mode `0644`) that runs the compile as `svc-metrics` on the runbook's exact schedule and job line;
- `/app/output` and `/var/log/metrics-rollup` owned `svc-metrics:svc-metrics` at mode `0750` (a world-writable output or log directory is a rollout defect);
- the `/etc/logrotate.d/metrics-rollup` drop-in that actually rotates the compile logs, with the `su`/`create` directives that keep rotated files owned by `svc-metrics`;
- cleanup of the stale `/var/lock` lock and the unrotated `compile.log.0` leftover the crashed run left behind, keeping the live `compile.log`.

The runbook gives every name, path, mode and exact line. The scheduled compile must both run and rotate as `svc-metrics`, not as root.

**The rollup service (repair the compiler it runs).** The compiler at `/app/workflow/metric_rollup.py` ships broken and emits unsafe responder queues, so the recovered schedule would keep shipping bad pages until it is fixed. Repair it so, driven by `--input PATH --output-dir PATH` (defaults `/app/data/samples.json` and `/app/output`), it again writes `rollup_summary.json`, `gap_windows.json` and compact `alert_queue.jsonl`, matching `/app/docs/rollup_contract.json` exactly, remaining idempotent, and still working on a different sample input of the same shape. Leave the frozen reference snapshot `/app/workflow/.metric_rollup.original` unchanged.

How the compile is meant to behave is not in the contract. The change-advisory board settled it, and `/app/sample/rollup_review_log.md` is the record: normalization, dedupe, interval and overlap semantics, policy resolution and its sparse-field fallbacks, attenuation, the debt ledger, scoring, priority and ordering are all MET-ticketed entries there, and where two entries disagree the later dated decision governs. The `governing_entry_index` in `/app/docs/rollup_contract.json` enumerates, per pipeline stage, the exact MET tickets whose final rulings govern — including the deduplication tie-break chain and its later severity-direction reversal — so use it to jump straight to the governing entries instead of scanning the log linearly. Derive every rollup value from the input samples, the fixed source files and the board's rulings; do not hardcode results and do not copy them from any precomputed or expected-output file.
